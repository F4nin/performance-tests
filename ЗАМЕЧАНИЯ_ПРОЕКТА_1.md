## КРИТИЧЕСКИЕ ОШИБКИ

### 1. HTTP event hook ломает сбор метрик для успешных запросов
**Файл:** `clients/http/event_hooks/locust_event_hook.py`, строка 34

```python
response = response.raise_for_status()
```

Метод `httpx.Response.raise_for_status()` возвращает `None` в случае успеха и выбрасывает исключение при ошибке. На каждом успешном запросе `response` становится `None`. Затем на строках 38 (`response.request`) и 47 (`response.read()`) происходит `AttributeError: 'NoneType' object has no attribute 'request'`. Это исключение НЕ перехватывается блоком `except (HTTPError, HTTPStatusError)`, так как `AttributeError` не является подклассом `HTTPError`.

**Следствие:** Метрики Locust полностью сломаны для успешных HTTP-запросов. События `environment.events.request.fire()` никогда не вызываются для успешных ответов. Статистика Locust будет показывать только ошибочные запросы.

**Исправление:**
```python
response.raise_for_status()  # без присваивания
```

### 2. `abstract = True` наследуется всеми сценариями — Locust никогда их не запустит
**Файлы:** `tools/user.py`, строка 10; все классы сценариев

```python
class LocustBaseUser(User):
    abstract = True
```

Все наследники (`GetAccountsScenarioUser`, `GetDocumentsScenarioUser` и др.) наследуют `abstract = True` и ни один не переопределяет его на `abstract = False`. В Locust атрибут `abstract` наследуется, и runner пропускает все классы, где `abstract` является истинным.

**Следствие:** Ни один нагрузочный сценарий не будет выполнен. Все классы пользователей будут молча пропущены.

---

### 3. gRPC-интерцептор теряет метрики при не-RpcError исключениях
**Файл:** `clients/grpc/interceptors/locust_interceptor.py`, строки 33-41

```python
try:
    response = continuation(client_call_details, request)
    response_length = response.result().ByteSize()
except RpcError as error:
    exception = error
```

Блок `except` ловит только `grpc.RpcError`. Если `response.result()` выбросит любое другое исключение (например, `ValueError` при десериализации protobuf, `AttributeError`), оно не будет перехвачено, событие `environment.events.request.fire()` никогда не выполнится, метрика будет потеряна, а исключение пробросится в greenlet.

**Следствие:** Часть ошибок gRPC-вызовов невидима в отчётах Locust — статистика занижает реальное количество ошибок.

## СЕРЬЁЗНЫЕ ОШИБКИ

### 4. Синхронный вызов `.result()` внутри gRPC-интерцептора
**Файл:** `clients/grpc/interceptors/locust_interceptor.py`, строка 38

```python
response_length = response.result().ByteSize()
```

Вызов `.result()` блокирует текущий greenlet до получения ответа. Это допустимо только под gevent, но делает интерцептор непригодным для любого другого контекста. Кроме того, время CPU, потраченное на `ByteSize()` (сериализация protobuf), включается в `response_time`, искажая реальное сетевое время ответа. Правильный подход — использовать `response.add_done_callback()`.

---

### 5. Создание 5 независимых каналов/клиентов на каждого пользователя Locust
**Файлы:** `clients/grpc/gateway/locust.py`, `clients/http/gateway/locust.py`

Оба `GatewayGRPCTaskSet` и `GatewayHTTPTaskSet` в методе `on_start()` создают по 5 API-клиентов, каждый со своим собственным gRPC-каналом или HTTP connection pool к одному и тому же хосту. При 1000 одновременных пользователей это создаёт 5000 TCP-соединений вместо потенциальных 1000 (gRPC) или эффективного переиспользования connection pool (HTTP).

**Следствие:** Избыточный расход файловых дескрипторов и ресурсов сервера, потенциальное исчерпание портов.

---

### 6. Утечка ресурсов — отсутствует `on_stop` для закрытия каналов/клиентов
**Файлы:** `clients/grpc/gateway/locust.py`, `clients/http/gateway/locust.py`

Ни в одном из TaskSet-классов не реализован метод `on_stop()`. gRPC-каналы и httpx-клиенты, созданные в `on_start()`, никогда не закрываются явно. После завершения итерации пользователя они остаются висеть до сборки мусора, что при высокой нагрузке приводит к утечке соединений и файловых дескрипторов.

### 7. Все операции `make_*_operation` отправляют случайный статус
**Файлы:**
- `clients/grpc/gateway/operations/client.py`, строки 186-248
- `clients/http/gateway/operations/operations_schema.py`, строка 67

```python
status=fake.proto_enum(OperationStatus)  # gRPC
status: OperationStatus = Field(default_factory=lambda: fake.enum(OperationStatus))  # HTTP schema
```

Для операций создания (пополнение, покупка, перевод и т.д.) статус обычно устанавливается сервером (например, `IN_PROGRESS` или `PENDING`). Отправка случайного значения, включая `FAILED`, `COMPLETED`, может вызывать ошибки валидации на сервере, искусственно завышая процент ошибок в тестах.

**Файл:** `seeds/builder.py`, строки 193, 242


## ЗНАЧИТЕЛЬНЫЕ НЕДОСТАТКИ

### 11. Состояние гонки (race condition) при создании директории dumps
**Файл:** `seeds/dumps.py`, строки 15-16

```python
if not os.path.exists("dumps"):
    os.mkdir("dumps")
```

Классический TOCTOU (Time-Of-Check Time-Of-Use): между проверкой существования и созданием директории другой процесс может создать её, что вызовет `FileExistsError`. Также используется `os.mkdir` вместо `os.makedirs` — если отсутствует родительская директория, будет ошибка. Пути заданы относительно CWD, а не корня проекта.

**Исправление:**
```python
os.makedirs("dumps", exist_ok=True)
# или с pathlib:
Path("dumps").mkdir(exist_ok=True)
```

### 15. TaskSet с весами вместо SequentialTaskSet в сценариях счетов
**Файлы:** `grpc_locust_get_accounts.py`, `locust_get_accounts.py`, `scenarios/grpc/gateway/new_user_get_accounts/scenario.py`, `scenarios/http/gateway/new_user_get_accounts/scenario.py`

Все четыре файла используют `TaskSet` (не `SequentialTaskSet`) с весами задач (2, 2, 6). В `TaskSet` задачи выбираются случайным образом. Это значит, что `get_accounts` (вес 6) может выполниться до `create_user` (вес 2), что приведёт к холостому возврату (`if self.create_user_response is None: return`). При использовании же `SequentialTaskSet` веса игнорируются и задачи выполняются строго по порядку. Для сравнения: сценарии `get_documents` корректно используют `SequentialTaskSet`.

### 16. `SeedsScenario.build()` не возвращает результат, а `__init__` жёстко привязан к gRPC
**Файл:** `seeds/scenario.py`

```python
def __init__(self):
    self.builder = build_grpc_seeds_builder()  # Только gRPC, HTTP-фабрика не используется
```

### 23. `proto_enum()` может вернуть 0 (UNSPECIFIED)
**Файл:** `tools/fakers.py`, строка 123

```python
def proto_enum(self, value: EnumTypeWrapper) -> int:
    return self.faker.random_element(value.values())
```

`EnumTypeWrapper.values()` включает все целочисленные значения proto-enum, в том числе 0 (обычно `UNSPECIFIED`). Отправка 0 может быть отклонена сервером как невалидное значение. Значение по умолчанию следует фильтровать.

### 24. `email()` генерирует нестандартный формат
**Файл:** `tools/fakers.py`, строка 35

```python
return f"{time.time()}.{self.faker.email()}"
```

`time.time()` возвращает float вида `1765939200.123456`. Итоговый email: `1765939200.123456.user@example.com`. Хотя технически валидный, некоторые серверы могут отклонить такие адреса. Лучше использовать `int(time.time() * 1000)` или `uuid.uuid4()`.

### 31. `pop(0)` в `get_next_user` — O(n)
**Файл:** `seeds/schema/result.py`, строка 85

```python
return self.users.pop(0)
```

`list.pop(0)` имеет сложность O(n) из-за сдвига всех элементов в памяти. Для 1000+ пользователей эффективнее использовать `collections.deque.popleft()`.

Разные значения ожидания между созданием операции и получением чека. Ни одно из них не обосновано — нет гарантии, что чек будет готов через фиксированное время.

### 39. Отсутствие обработки ошибок во всех standalone-скриптах
**Файлы:** `grpcio_*.py`, `grpc_*.py`, `httpx_*.py`

Ни в одном из корневых скриптов нет try/except для gRPC/HTTP-вызовов. Любая сетевая ошибка или ошибка сервера приводит к необработанному исключению.

---

### 40. Отсутствие `channel.close()` в standalone-скриптах
**Файлы:** `grpcio_*.py`, `grpc_*.py`

Все скрипты, использующие gRPC, создают канал через `grpc.insecure_channel()`, но ни один не вызывает `channel.close()`. Ресурсы освобождаются только при завершении процесса.

---

### 41. Dockerfile устанавливает только `redis`
**Файл:** `Dockerfile`

```dockerfile
RUN pip install redis
```

Dockerfile не устанавливает основные зависимости проекта (locust, grpcio, httpx, pydantic, faker). Контейнер не сможет запустить ни один сценарий. Также `COPY . .` копирует `.venv/`, `__pycache__/`, `.git/` — нужен `.dockerignore`.

---

### 42. `docker-compose.yml` — ошибка форматирования
**Файл:** `docker-compose.yml`

Присутствуют лишние пустые строки внутри определения сервиса, неоднородные отступы. Конфигурация может не разбираться некоторыми версиями Docker Compose.

---

### 43. `locust_event_hook.py` — избыточный перехват исключений
**Файл:** `clients/http/event_hooks/locust_event_hook.py`, строка 35

```python
except (HTTPError, HTTPStatusError) as error:
```

`HTTPStatusError` является подклассом `HTTPError`, поэтому отдельное его указание избыточно. Достаточно `except HTTPError`.

---

### 44. `greeting.proto` и сгенерированные файлы — мёртвый код
**Файлы:** `greeting.proto`, `greeting_pb2.py`, `greeting_pb2_grpc.py`, `grpc_client.py`, `grpc_server.py`

Демонстрационный "Hello World" protobuf, не имеющий отношения к домену проекта (банковский шлюз). Сервер и клиент Greeter не используются ни в одном сценарии.
